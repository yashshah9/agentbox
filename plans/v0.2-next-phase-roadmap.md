## 1. Executive summary

v0.2 transforms agentbox from a **development prototype** into a **production-capable self-hosted sandbox platform**. The roadmap delivers six milestones in dependency order: kernel-level isolation (gVisor), latency reduction (warm pool), stateful workspaces (snapshot/restore), multi-runtime support (Node.js), network hardening (default-deny egress), and developer ecosystem expansion (TypeScript SDK + resource limits API).

Each milestone is independently shippable behind feature flags and backend selectors, allowing incremental rollout without blocking the full v0.2 release train.

---

## 2. Strategic goals

| Goal | Success metric |
|------|----------------|
| Production-grade isolation | Untrusted code cannot access host filesystem, network (by default), or other tenants |
| Sub-second warm execution | P50 latency < 500 ms for pooled Python/Node runs (excluding user code runtime) |
| Stateful agent workflows | Snapshot → mutate → restore cycle completes in < 2 s for 100 MB workspace |
| Multi-runtime parity | Node.js runs achieve same API contract as Python |
| Safe-by-default networking | Zero egress unless explicitly allowlisted |
| Broad SDK adoption | TypeScript SDK published; feature parity with Python SDK |

## 4. Cross-cutting requirements (all milestones)

- **Backend abstraction:** Extend `SandboxBackend` protocol; select via `AGENTBOX_SANDBOX_BACKEND=runsc|subprocess`.
- **Feature flags:** New capabilities gated by env vars until stable; subprocess backend remains for local dev.
- **Observability:** Structured logs (structlog) with `run_id`, `backend`, `duration_ms`, `pool_hit` fields.
- **Backward compatibility:** `POST /v1/run` request/response schema unchanged; new fields are additive only.
- **Testing:** Each milestone adds ≥3 integration tests; CI runs against gVisor-capable runner (Linux + KVM).
- **Documentation:** README, OpenAPI, and SDK docs updated per milestone.

## M1 — gVisor runsc backend

### Objective

Replace subprocess isolation with **gVisor `runsc`** OCI runtime so untrusted code executes in a user-space kernel with a separate mount/network namespace.

### Deliverables

1. **`RunscSandbox` backend** implementing the shared sandbox interface (`run_python`, future `run_node`).
2. **OCI bundle builder** — construct `config.json` + rootfs for each execution (or pool slot).
3. **Rootfs image** — minimal Python 3.11 base (`docker/Dockerfile.runsc-rootfs`).
4. **Runtime integration** — invoke `runsc run` with flags: `--network=none` (initial), read-only rootfs, tmpfs workspace mount.
5. **Config additions:**
   - `AGENTBOX_SANDBOX_BACKEND=runsc`
   - `AGENTBOX_RUNSC_BINARY=/usr/local/bin/runsc`
   - `AGENTBOX_ROOTFS_IMAGE=agentbox-rootfs:latest`
6. **Migration path** — `/health` reports `backend: runsc`; subprocess remains available for dev.
7. **CI job** — Linux runner with gVisor installed; smoke test executes `print(1)` via runsc.
8. **Security documentation** — threat model doc comparing subprocess vs runsc boundaries.

### Acceptance criteria

- [ ] `POST /v1/run` with `backend=runsc` executes Python code; stdout/stderr/exit_code returned correctly.
- [ ] Attempt to read `/etc/passwd` from sandbox fails (no host filesystem leak).
- [ ] Attempt to bind/listen on network fails with `--network=none`.
- [ ] Execution timeout kills runsc container within `timeout + 2s` grace.
- [ ] `/health` returns `"backend": "runsc"` when configured.
- [x] Subprocess backend still works when `AGENTBOX_SANDBOX_BACKEND=subprocess`.
- [ ] ≥5 integration tests pass in CI (happy path, timeout, exit non-zero, output cap, isolation).

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| gVisor incompatible with host kernel | Medium | High | Document supported kernel versions; CI matrix on Ubuntu 22.04/24.04 |
| runsc startup latency (>2s cold) | High | Medium | M2 warm pool directly addresses; set expectations in v0.2.0 release notes |
| OCI bundle complexity | Medium | Medium | Start with `runsc do` / minimal spec; iterate |
| macOS dev machines cannot run runsc | High | Low | Subprocess fallback; document Linux requirement for production |
| Debugging sandbox failures is hard | Medium | Medium | Capture runsc logs; expose `run_id` in error responses |

### Estimate

| Phase | Duration |
|-------|----------|
| Design + threat model | 2 days |
| OCI bundle + runsc integration | 8 days |
| Rootfs image + Docker updates | 3 days |
| Tests + CI (gVisor runner) | 4 days |
| Docs + review | 2 days |
| **Total** | **~3 weeks** |

## M2 — Warm pool pre-warmed sandboxes

### Objective

Maintain a pool of **pre-initialized runsc containers** (or paused bundles) to eliminate cold-start latency for high-frequency agent tool calls.

### Deliverables

1. **`SandboxPool` manager** — configurable pool size, idle TTL, and replenishment worker.
2. **Pool lifecycle:**
   - **Warm:** container booted, Python/Node runtime ready, workspace tmpfs mounted.
   - **Checkout:** assign slot to incoming `POST /v1/run` request.
   - **Checkin:** reset workspace (see M3 for snapshot-aware reset), return to pool or destroy if unhealthy.
3. **Config additions:**
   - `AGENTBOX_POOL_SIZE=4` (default)
   - `AGENTBOX_POOL_IDLE_TTL_SECONDS=300`
   - `AGENTBOX_POOL_WARMUP_ON_START=true`
4. **Metrics exposure** — pool size, available slots, checkout wait time (logged; optional `/metrics` stub for future Prometheus).
5. **Graceful shutdown** — drain pool on SIGTERM before exit.
6. **API additive field** — `pool_hit: bool` in `RunResponse` (optional, default omitted for backward compat).

### Acceptance criteria

- [ ] With `POOL_SIZE=4`, four concurrent requests complete without cold-start runsc init.
- [ ] P50 checkout latency < 100 ms when pool has available slots (measured in integration bench test).
- [ ] Pool replenishes automatically after slot consumption.
- [ ] Unhealthy slots (crash, timeout) are evicted and replaced.
- [ ] Server starts cleanly with `POOL_WARMUP_ON_START=true`; `/health` OK after warmup.
- [ ] Pool respects global concurrency cap; excess requests queue or return 503 with `Retry-After` (configurable).
- [ ] ≥4 integration tests: pool hit, pool miss (cold fallback), eviction, concurrent checkout.

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Memory pressure from idle containers | High | High | Configurable pool size; idle TTL; document RAM = pool_size × rootfs footprint |
| State leakage between checkouts | Medium | Critical | Mandatory workspace wipe on checkin; add regression test |
| Pool deadlock under load | Low | High | Timeouts on checkout; circuit breaker to cold path |
| runsc pause/resume not stable | Medium | Medium | Fall back to destroy-and-recreate if resume fails |

### Estimate

| Phase | Duration |
|-------|----------|
| Pool manager design | 2 days |
| Checkout/checkin + warmup | 6 days |
| Concurrency + eviction | 3 days |
| Benchmark + tests | 3 days |
| Docs | 1 day |
| **Total** | **~2 weeks** |

**Depends on:** M1 (runsc backend).

## M3 — Snapshot/restore filesystem

### Objective

Enable agents to **capture workspace state** (files written during execution) and **restore** it into a subsequent sandbox run — supporting multi-step coding workflows without re-uploading context.

### Deliverables

1. **Snapshot API:**
   - `POST /v1/snapshots` — create snapshot from active or last-used workspace; returns `snapshot_id`.
   - `GET /v1/snapshots/{id}` — metadata (size, created_at, runtime).
   - `DELETE /v1/snapshots/{id}` — reclaim storage.
2. **Restore integration:**
   - `POST /v1/run` accepts optional `snapshot_id` to seed workspace before execution.
   - Pool checkin optionally auto-snapshots (configurable).
3. **Storage backend** — local directory (`AGENTBOX_SNAPSHOT_DIR`) with content-addressed tar.zst archives; pluggable interface for S3 later.
4. **Size limits** — `AGENTBOX_SNAPSHOT_MAX_BYTES` (default 500 MB); reject oversize with 413.
5. **Garbage collection** — TTL-based cleanup (`AGENTBOX_SNAPSHOT_TTL_HOURS=24`).
6. **Python SDK updates** — `client.create_snapshot()`, `client.run(code, snapshot_id=...)`.

### Acceptance criteria

- [ ] Run code that writes `output.txt` → snapshot → new run with `snapshot_id` → file contents preserved.
- [ ] Snapshot size reported in metadata; oversize snapshot rejected.
- [ ] Restore + run completes in < 2 s for 100 MB workspace (benchmark test, Linux CI).
- [ ] Deleted snapshot returns 404 on restore attempt.
- [ ] Snapshots isolated per tenant ID when auth is added (design hook; single-tenant OK for v0.2).
- [ ] ≥5 tests: create, restore, delete, TTL expiry, size limit.

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Snapshot storage growth | High | Medium | TTL GC; max count per node; compression (zstd) |
| Inconsistent state if snapshotted mid-run | Medium | High | Only snapshot on clean checkin; document semantics |
| Cross-platform tar metadata issues | Low | Medium | Normalize permissions; test round-trip |
| Slow restore negates pool benefits | Medium | Medium | Layer snapshot onto pooled slot; benchmark in CI |

### Estimate

| Phase | Duration |
|-------|----------|
| Storage format + API design | 3 days |
| Snapshot create/restore impl | 8 days |
| GC + limits | 2 days |
| SDK + tests | 4 days |
| Docs | 2 days |
| **Total** | **~3 weeks** |

**Depends on:** M1. **Recommended after:** M2 (pool checkin is natural snapshot point).

## M4 — Node.js runtime

### Objective

Execute **JavaScript/TypeScript (via Node)** in the same sandbox infrastructure as Python, using an identical API contract.

### Deliverables

1. **Runtime dispatch** — `POST /v1/run` with `"language": "node"` executes via `node` in runsc rootfs.
2. **Rootfs update** — Node.js LTS (20.x) added to runsc rootfs image.
3. **`run_node(code)` method** on sandbox backend interface.
4. **Entry convention** — user code wrapped as inline `-e` script or temp `main.mjs` (ESM default).
5. **Pool warmup** — Node slots pre-warmed alongside Python (config: `AGENTBOX_POOL_RUNTIMES=python,node`).
6. **Error mapping** — syntax errors surface in `stderr` with non-zero `exit_code` (same as Python).
7. **SDK update** — `client.run(code, language="node")`.

### Acceptance criteria

- [x] `POST /v1/run` with `language: node` / `javascript` executes `console.log('hello')` → stdout contains `hello`.
- [ ] Node `require()` of built-in modules works (`fs`, `path`); native addons blocked or documented as unsupported.
- [x] Timeout and output cap behave identically to Python runs.
- [x] Unsupported language still returns 400.
- [ ] Pooled Node runs achieve same latency characteristics as Python (M2).
- [x] Tests: happy path (Node in Docker image), timeout, unsupported language.

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Node rootfs increases image size | High | Low | Multi-stage rootfs; slim Node distroless base |
| npm/network needed for packages | Medium | Medium | Defer package install to v0.3; document no npm in v0.2 |
| ESM vs CJS confusion | Medium | Low | Default to `.mjs` ESM; document convention |
| Dual-runtime pool complexity | Medium | Medium | Separate sub-pools per runtime or unified with runtime tag |

### Estimate

| Phase | Duration |
|-------|----------|
| Rootfs + runsc Node integration | 4 days |
| API dispatch + backend method | 2 days |
| Pool warmup for Node | 3 days |
| Tests + SDK | 3 days |
| Docs | 1 day |
| **Total** | **~2 weeks** |

**Depends on:** M1. **Recommended:** M2 for acceptable latency.

## M5 — Default-deny egress

### Objective

Block all outbound network traffic from sandboxes **by default**, with an explicit per-request or per-policy allowlist for approved destinations.

### Deliverables

1. **Default policy** — runsc containers start with `--network=none` (or isolated namespace with iptables DROP).
2. **Allowlist config:**
   - Global: `AGENTBOX_EGRESS_ALLOWLIST=api.openai.com:443,pypi.org:443`
   - Per-request override: `POST /v1/run` accepts optional `egress_allowlist: string[]` (subset of global).
3. **DNS resolution** — controlled resolver or `/etc/hosts` injection for allowed hosts only.
4. **Egress proxy sidecar (optional)** — lightweight userspace proxy enforcing SNI/port rules if `--network=none` is too restrictive for allowlist.
5. **Audit logging** — log blocked egress attempts with destination (for debugging; no PII).
6. **Documentation** — network policy guide for self-hosters.

### Acceptance criteria

- [ ] Default config: `curl https://example.com` inside sandbox fails.
- [ ] With allowlist `example.com:443`, HTTPS GET to example.com succeeds.
- [ ] Non-allowlisted host returns clear error in stderr or sandbox log.
- [ ] Per-request allowlist cannot exceed global allowlist (security: no privilege escalation).
- [ ] Python `urllib` and Node `fetch` behave consistently under policy.
- [ ] ≥5 tests: block default, allow single host, block non-allowlisted, DNS leak prevention, per-request subset.

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| gVisor network stack limitations | Medium | High | Spike egress proxy approach early; fallback to iptables in namespace |
| DNS rebinding / bypass | Medium | High | Resolve to IP at policy layer; short TTL re-resolve |
| Allowlist UX too complex | Medium | Medium | Sensible defaults; document common AI API endpoints |
| Breaks legitimate package installs | High | Low | Document that npm/pip install requires v0.3 egress policy |

### Estimate

| Phase | Duration |
|-------|----------|
| Network policy design | 2 days |
| runsc/network namespace impl | 5 days |
| Allowlist + per-request API | 3 days |
| Tests + docs | 3 days |
| **Total** | **~2 weeks** |

**Depends on:** M1. **Can parallelize with:** M4 after M1 complete.

## M6 — TypeScript SDK + resource limits API

### Objective

Ship a **TypeScript/JavaScript SDK** with feature parity to the Python client, and expose a **resource limits API** so callers can cap CPU time, memory, and (optionally) wall-clock per execution.

### Deliverables

#### TypeScript SDK

1. **Package** — `@agentbox/sdk` published to npm.
2. **Client class** — `AgentboxClient` with `health()`, `run()`, `createSnapshot()` (if M3 shipped).
3. **Types** — full TypeScript types for request/response models; exported from package.
4. **Runtime** — works in Node 18+; fetch-based (no hard dependency on axios).
5. **Tests** — vitest unit tests + optional integration test against local server.

#### Resource limits API

1. **Request schema extension:**

   ```json
   {
     "code": "...",
     "language": "python",
     "limits": {
       "timeout_seconds": 30,
       "memory_mb": 512,
       "cpu_ms": 10000
     }
   }
   ```

2. **Enforcement** — cgroups v2 inside runsc container:
   - `memory.max` from `memory_mb`
   - `cpu.max` or `cpu.max.burst` from `cpu_ms` / `timeout_seconds`
3. **Response extension** — `limits_applied: { memory_mb, timeout_seconds }` and `oom_killed: bool`.
4. **Defaults** — server-level defaults via env; per-request overrides capped by server max (prevent escalation).
5. **Config:**
   - `AGENTBOX_MAX_MEMORY_MB=1024`
   - `AGENTBOX_MAX_TIMEOUT_SECONDS=120`
6. **Python SDK update** — `run(code, limits={...})` parameter.

### Acceptance criteria

- [ ] `@agentbox/sdk` installs via npm; `client.run('print(1)')` works against v0.2 server.
- [x] TypeScript client source at `sdk/ts/client.ts` (fetch-based; not published to npm yet).
- [x] Python SDK `run(..., timeout_seconds=)` and API `limits.timeout_seconds`.
- [ ] `limits.memory_mb=64` causes OOM kill on `bytearray(10**9)` allocation; `oom_killed: true` in response.
- [ ] Per-request limits cannot exceed server-configured maximums (returns 400).
- [ ] Both Python and TypeScript SDKs pass same integration test vectors.
- [x] Tests: SDK instantiation, per-request timeout → 408.

### Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| cgroups not available in all deploy envs | Medium | High | Detect at startup; degrade gracefully with warning |
| Memory limit false positives | Low | Medium | Integration tests with known allocations |
| npm package naming conflict | Low | Low | Scoped package `@agentbox/sdk` |
| OpenAPI drift between SDKs | Medium | Medium | Generate types from OpenAPI spec in CI |

### Estimate

| Phase | Duration |
|-------|----------|
| Resource limits API + cgroups | 5 days |
| TypeScript SDK | 4 days |
| Python SDK limits param | 1 day |
| Cross-SDK tests + npm publish | 3 days |
| Docs | 1 day |
| **Total** | **~2 weeks** |

**Depends on:** M1 (cgroups in runsc). **SDK parity:** M4 (Node runtime) should ship before or with M6.
